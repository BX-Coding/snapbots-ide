# Multi-device session — backend contract

**Audience:** the SnapBots Modal backend repo (`endpoints/modal/modal_endpoint.py` and friends).
**Purpose:** spec out a new session layer on top of the existing per-environment `POST /generation` flow so that remote phones can upload paper-diagram photos into a shared session hosted by a SnapBots IDE tab.
**Status:** frontend-side design is finalized; backend implementation is open. Treat the "Open questions" section at the bottom as discussion items, not blockers.

---

## 1. Goal & user flow

A host (teacher) opens the SnapBots IDE, clicks "Start Multi-Device Session", and gets a **6-digit session code** + a join URL (`<frontend-host>/join/<code>`). They display the code or QR to the room. Each phone opens the URL, types a display name, takes a photo of a paper state-diagram, and submits. Phones never see the host's project — they only see "queued → processing → ✅ added" status for their own submission. The host IDE listens for completed submissions and, for each one, creates a new sprite in the project with the submitter's name and the generated code/costumes/sounds.

The host picks the environment mode (`simulation` / `hybrid` / `soccer`) when they start the session; that mode is locked for the session's lifetime. All submissions in a session route through whichever primitive set + `additional_context` matches the session's mode.

---

## 2. What changes vs. today

**Unchanged:**
- `endpoints/modal/modal_endpoint.py:51` `generation_with_primitives()` — the core image→code pipeline. The session layer calls this; it does not modify it.
- `endpoints/inc/classes/format.py` `GenerationRequest` and `GenerationResponse` models.
- The existing `POST /generation` endpoint on the three ASGI apps (`hybrid`, `simulation`, `soccer`) — kept for the single-device IDE flow.
- `detection_pipeline/`, `code_generation/`, the primitive modules.
- The `bot_queue` (`modal.Queue`) flow for physical-robot polling — independent.

**New:**
- A session/submission HTTP API (see §4) implemented as a new ASGI app (recommended: `snapbot-session`) or attached to an existing app.
- A `modal.Dict` named `sessions` and one named `submissions` (see §3).
- An async wrapper that calls `generation_with_primitives.spawn(...)` per submission and writes the result back into `submissions[id]` when done.
- A cleanup cron that expires idle sessions and drops stale submission records.

This layer is **pure orchestration** above the existing pipeline. No changes to vision, LLM prompts, primitive sets, or response shape.

---

## 3. Data model

Two new `modal.Dict` instances.

### `sessions[session_id] -> Session`

```python
class Session(TypedDict):
    session_id: str                    # 6-digit numeric, e.g. "482917"
    mode: Literal["simulation", "hybrid", "soccer"]
    host_id: str                       # opaque host-generated UUID, used for ownership checks on /end
    created_at: str                    # ISO 8601 UTC
    last_activity_at: str              # ISO 8601 UTC, bumped on any read or write
    status: Literal["active", "ended", "expired"]
    submission_cap: int                # default 50
    submission_ids: list[str]          # ordered, append-only
```

### `submissions[submission_id] -> Submission`

```python
class Submission(TypedDict):
    submission_id: str                 # UUID4
    session_id: str
    submitter_name: str                # joiner-provided display name, max 64 chars
    status: Literal["queued", "processing", "done", "failed"]
    submitted_at: str                  # ISO 8601 UTC
    modal_call_id: str | None          # from function.spawn(); for status reaping
    result: GenerationResponse | None  # populated when status == "done"
    error: str | None                  # populated when status == "failed"
```

Notes:
- Sessions and submissions are stored in **separate** dicts so that listing/polling sessions doesn't pull the (potentially heavy) `result` payloads into memory.
- `submission_ids` on the session is append-only and ordered by submission time so the host can render a stable feed.
- `result` carries the full existing `GenerationResponse` unchanged — same shape today's `/generation` endpoint returns. Frontend already knows how to consume it.

## 4. HTTP API

All endpoints return JSON unless noted. All times are ISO 8601 UTC. All session lookups must bump `last_activity_at`.

### 4.1 `POST /session` — host creates a session

**Request:**
```json
{
  "mode": "simulation" | "hybrid" | "soccer",
  "host_id": "<opaque UUID generated by frontend>"
}
```

**Response (201):**
```json
{
  "session_id": "482917",
  "mode": "simulation",
  "created_at": "2026-05-26T18:42:11Z",
  "submission_cap": 50
}
```

**Backend responsibility:**
- Generate `session_id` by rejection sampling: random 6-digit string, retry if collides with an existing **active** session. Sessions in `ended` or `expired` status can have their codes recycled.
- Persist Session record with `status="active"`, `submission_ids=[]`, `last_activity_at=created_at`.

### 4.2 `GET /session/{session_id}` — host polls (every ~3 seconds)

**Response (200):**
```json
{
  "session_id": "482917",
  "mode": "simulation",
  "status": "active",
  "created_at": "...",
  "last_activity_at": "...",
  "submissions": [
    {
      "submission_id": "uuid-1",
      "submitter_name": "Alice",
      "status": "done",
      "submitted_at": "..."
    },
    {
      "submission_id": "uuid-2",
      "submitter_name": "Bob",
      "status": "processing",
      "submitted_at": "..."
    }
  ]
}
```

**Errors:**
- `404 SESSION_NOT_FOUND` if `session_id` doesn't exist.
- Returns the session even if `status` is `ended` or `expired` so the host UI can render a final state — only `404` for truly unknown codes.

**Notes:**
- The submissions array is summary-only (no `result`, no `error` body). Host fetches the full result via §4.5 once it sees a submission transition to `done` or `failed`.

### 4.3 `POST /session/{session_id}/end` — host closes a session

**Request:**
```json
{ "host_id": "<must match the host_id from /session creation>" }
```

**Response (200):**
```json
{ "session_id": "482917", "status": "ended" }
```

**Errors:**
- `404 SESSION_NOT_FOUND`
- `403 NOT_HOST` if `host_id` doesn't match the recorded `host_id`.

**Behavior:**
- Sets `status="ended"`. Future submit attempts return `409 SESSION_ENDED`.
- Queued/processing submissions can be allowed to complete (their results are still readable) or be canceled — backend's call. Recommendation: let them complete; the host UI handles stragglers gracefully.

### 4.4 `POST /session/{session_id}/submit` — phone submits a photo

**Request:** `multipart/form-data`
- `image` (file): the photo. Server must reject `Content-Length > 10 MB` and any `Content-Type` not matching `image/*`.
- `submitter_name` (string): max 64 chars; trim whitespace; reject empty.

Multipart (not base64 JSON) so 2–8 MB phone JPEGs don't get 33% inflated over cell networks.

**Response (202):**
```json
{
  "submission_id": "uuid-...",
  "status": "queued",
  "session_id": "482917"
}
```

**Errors:**
- `404 SESSION_NOT_FOUND`
- `409 SESSION_ENDED` if status is `ended`
- `410 SESSION_EXPIRED` if status is `expired`
- `429 RATE_LIMITED` if this submitter has submitted within the last 30s (see §6)
- `409 SUBMISSION_CAP_REACHED` if `len(submission_ids) >= submission_cap`
- `413 IMAGE_TOO_LARGE` if file > 10 MB
- `415 UNSUPPORTED_MEDIA_TYPE` if not `image/*`

**Backend responsibility:**
1. Validate session, caps, rate limit.
2. Create a Submission record with `status="queued"`, append `submission_id` to `session.submission_ids`.
3. Base64-encode the image bytes and spawn the generator:
   ```python
   call = generation_with_primitives.spawn(
       uuid=submission_id,
       image=image_base64,
       characters=[],  # joiner has no project state; see §6
       global_vars={"current_message": "none"},
       mode=session.mode,  # determines primitive set + additional_context
   )
   submission.modal_call_id = call.object_id
   submission.status = "processing"
   ```
4. Return 202 immediately. Do NOT block on the generation.
5. When the spawned call completes (either via a callback or via the cleanup cron polling `modal_call_id` status — backend's choice), set `submission.status = "done"` and `submission.result = <GenerationResponse>`, or `status = "failed"` and `error = <message>`.

### 4.5 `GET /session/{session_id}/submission/{submission_id}` — fetch full submission

Used by both the host (after it sees `status` go to `done`/`failed` in the summary list) and the joiner phone (for its own status polling).

**Response (200):** the full `Submission` record, including `result` if done or `error` if failed.

**Errors:**
- `404 SUBMISSION_NOT_FOUND` if either the session or submission ID is unknown.

## 5. Async execution detail

Phone POSTs are fire-and-forget by design — they get a `submission_id` back in <500ms and poll. The actual generation runs as a `function.spawn()`:

```python
@app.function(image=base_image, secrets=[...])
def generation_with_primitives(uuid, image, characters, global_vars, mode):
    # existing implementation, untouched
    ...

# Inside the submit handler:
call = generation_with_primitives.spawn(
    uuid=submission_id, image=image_b64,
    characters=[], global_vars={"current_message": "none"}, mode=session.mode,
)
submissions[submission_id]["modal_call_id"] = call.object_id
submissions[submission_id]["status"] = "processing"
```

**Reaping completed calls** — two options, both fine:

- **A. Status polling cron** (simpler, recommended for v1): a `@modal.function(schedule=modal.Period(seconds=10))` cron iterates submissions with `status == "processing"`, calls `modal.functions.FunctionCall.from_id(modal_call_id).get(timeout=0)`, and writes back the result or exception.
- **B. Inline await in a separate background task** per submission. Lower latency but more moving parts.

If you go with cron, the 10s polling cadence is the dominant source of end-to-end latency for the joiner. Drop it lower if joiner UX feels sluggish.

## 6. Defaults the backend should apply for session submissions

The existing `GenerationRequest` model requires `characters` and `global_vars`. Joiners have no project context, so the backend fills them in:

| Field | Today (`/generation`) | Session submit (`/session/{id}/submit`) |
|---|---|---|
| `uuid` | caller-provided sprite target ID | server-generated `submission_id` (UUID4) |
| `image` | base64 in JSON body | bytes from multipart; backend base64s before calling `generation_with_primitives` |
| `characters` | caller-provided | always `[]` |
| `global_vars` | caller-provided, must include `current_message` | always `{"current_message": "none"}` |
| `mode` | implied by which ASGI app was hit | read from `session.mode` |

The `name` field on the resulting `GenerationResponse` is preserved as-is — but note that the host will overwrite the sprite's display name with the joiner's `submitter_name` when it applies the result. Backend doesn't need to know about this; just keep populating `name` like today.

## 7. Abuse / cost controls

- **Per-session submission cap.** Default `submission_cap=50`. Configurable per session (frontend doesn't expose this yet, but the field is there). Returns `409 SUBMISSION_CAP_REACHED` when hit.
- **Per-joiner rate limit.** Bucket by `(session_id, submitter_name)`, max 1 submission per 30 seconds, return `429 RATE_LIMITED`. Use a separate small `modal.Dict` keyed by `(session_id, submitter_name)` storing last-submit timestamp. This is best-effort — the bucket key is trust-on-display-name, which a determined attacker can bypass by changing names. That's fine: the per-session cap is the real cost cap.
- **Image size cap.** Reject multipart uploads >10 MB at the route, before reading the body if possible.
- **Content-type check.** `image/*` only; reject everything else.
- **Session expiry.** Every endpoint that touches a session must bump `last_activity_at`. A `@modal.function(schedule=modal.Period(minutes=30))` cron marks sessions with `last_activity_at > 4h ago` as `expired` and deletes their submission records from the `submissions` dict (keep the session record itself around for ~24h so a stale poll gets a clear `expired` status instead of a confusing `404`).
- **Session codes.** 6-digit numeric, ~10⁶ keyspace. Combined with the 4h expiry and per-joiner rate limit, this is acceptable for classroom use. If abuse becomes a problem, the right mitigations are (a) shorter session TTL, (b) a CAPTCHA on `/submit`, or (c) host-issued single-use joiner tokens — **not** lengthening the code (which would hurt the read-aloud UX that's the whole point).
- **OpenAI cost monitoring.** If you already have per-call cost tracking, recommend adding a `session_id` tag to the spans so a runaway session can be diagnosed quickly.

## 8. Error response shape

All non-2xx responses use this shape:

```json
{
  "error": "Human-readable message",
  "code": "MACHINE_READABLE_CODE",
  "details": "optional extra string"
}
```

Codes used by the frontend:

| HTTP | `code` | When |
|---|---|---|
| 400 | `INVALID_REQUEST` | Missing/malformed fields, empty submitter_name, etc. |
| 403 | `NOT_HOST` | `/end` called with wrong `host_id` |
| 404 | `SESSION_NOT_FOUND` | Unknown `session_id` |
| 404 | `SUBMISSION_NOT_FOUND` | Unknown `submission_id` (or session) |
| 409 | `SESSION_ENDED` | Submit attempted on ended session |
| 410 | `SESSION_EXPIRED` | Submit attempted on expired session |
| 409 | `SUBMISSION_CAP_REACHED` | Per-session cap hit |
| 413 | `IMAGE_TOO_LARGE` | Upload >10 MB |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | Non-image upload |
| 429 | `RATE_LIMITED` | Per-joiner rate limit hit |
| 500 | `GENERATION_FAILED` | Internal — also the value of `submission.error` when `status="failed"` |

Failed submissions stay in the record with `status="failed"` and a populated `error`. The host UI surfaces "Alice's submission failed: …" rather than silently dropping it.

## 9. Frontend touchpoints (FYI for cross-repo debugging)

When something goes wrong end-to-end, these are the frontend files calling your endpoints:

- `src/lib/snapbotSession.ts` — the HTTP client. `createSession`, `endSession`, `subscribeToSubmissions`, `fetchSubmission`, `submitPhoto`, `pollSubmissionStatus`.
- `api/modal/session/create.js`, `api/modal/session/[id]/index.js`, `api/modal/session/[id]/submit.js`, `api/modal/session/[id]/submission/[subId].js` — Vercel serverless proxies that forward browser → Modal (keeps your URL out of the browser bundle). Each is ~40 lines and mirrors the existing `api/modal/{simulation,hybrid,soccer}.js` pattern.
- `webpack.config.js` — dev-time proxy block, also points `/api/modal/session/*` at the Modal session host.

If the backend's Modal endpoint URL changes, all three files above need updating in lockstep — same as today's `/generation` endpoints.

## 10. Open questions for the backend dev

These are intentionally left open — please weigh in based on what's cheapest in your repo:

1. **App layout.** Does the session layer live in a new `snapbot-session` ASGI app, or fold into `simulation`? New app keeps the modal.Dict namespaces isolated (matches the existing per-environment pattern); folding into `simulation` saves a deployment. **Frontend preference: new app**, but no hard requirement.
2. **Image storage.** Submissions in `modal.Dict` keep the image only transiently (just long enough to base64 it for `generation_with_primitives.spawn`). Do you want to persist the original image to `modal.Volume` or S3 for debugging/replay, or is "process and discard" fine? Frontend doesn't need access to the original image.
3. **Spawn-result reaping.** Cron poll (option A in §5) or per-submission background await (option B)? Recommend cron for v1.
4. **Session record TTL after expiry.** I suggested keeping the session record itself for ~24h after expiry so polls get a clear `410 SESSION_EXPIRED` rather than `404 SESSION_NOT_FOUND`. Reasonable, or simpler to just delete?
5. **`host_id` durability.** If a host clears localStorage mid-session, they lose the ability to call `/end`. Acceptable (the 4h expiry will catch it), or should we instead issue a host-side bearer token at `/session` creation and require it on `/end`? Frontend can store either; tokens are slightly safer.
6. **Submission cap configurability.** Should `POST /session` accept an optional `submission_cap` so the frontend can expose it later, or hardcode 50 for now? I'd add the field but default to 50.
7. **Mode-specific contexts on session submissions.** Today the three ASGI apps each have their own `additional_context` string baked in. For session submissions, the dispatch happens dynamically based on `session.mode`. Make sure all three context strings remain reachable from the session handler (or refactor them into a `MODE_CONTEXTS[mode]` map).
8. **Cost telemetry.** If a per-session cost tag would help your dashboarding, the `session_id` is available on every spawn call — adding it to whatever tracing you already do is cheap.

## 11. Quick mental model

```
                 ┌────────────────────────┐
  Host IDE       │ POST /session          │  ──► sessions["482917"] = {mode, ...}
   (browser) ────┤ GET  /session/{id}     │  ──► poll for new submission_ids
                 │ GET  /session/{id}/.../{subId}   ──► fetch full result, apply to VM
                 │ POST /session/{id}/end │
                 └────────────────────────┘
                              │
                              │ (the only thing tying them together is session_id)
                              ▼
  Phone joiner   ┌────────────────────────┐
   (browser) ────┤ POST /session/{id}/submit (multipart image + name)
                 │ GET  /session/{id}/submission/{subId}  ──► poll my own status
                 └────────────────────────┘
                              │
                              ▼ (inside the submit handler)
                  generation_with_primitives.spawn(...)  ◄── existing pipeline, unchanged
                              │
                              ▼ (reaped by cron or callback)
                  submissions[subId].result = GenerationResponse
```
